## 4. Declared Gateway inputs consumed, and the fields that are missing

Consumed and rendered today, per capability: `capability_id`, `label`, `effect`
(`read`/`write`), `target_requirement`, `input_contract`, `evidence_requirement`
(`gateway_audit`). Per target: `target_ref`, `label`, `access`, `capability_ids`,
`grant_ref`, `grant_revision`, `readiness`. Protocol input provenance comes from
the release manifest's producer `repository`/`commit`/`tree`, which is why the
client never resolves the artifact by version alone.

The policy distinctions the request asks the client to keep visible **cannot be
rendered from the current descriptor**. Rather than invent a client-side
substitute, here are the exact fields needed:

1. **`scope_statement`** (per capability, or per capability×target) — a
   Gateway-authored, human-readable bound: "the named organization shared drive
   and directly shared files", "channels where the app is a member", "the
   connected top-level page and its allowed descendants". Today only an opaque
   `grant_ref`/`grant_revision` exists; the client can show that a grant exists
   but cannot say what it bounds, which is precisely the generic
   read/write promise the request forbids.
2. **`provider_application_authority`** (per capability) — which installed
   provider application's manifest authority backs this capability, so
   `github.issue.comment.create` cannot be read as implying pull-request
   creation or administration.
3. **`explicit_request_required`** (boolean, per capability) — marking every
   write/delete/move/permission change as requiring an explicit requester
   instruction. `effect: write` is not the same statement.
4. **`provenance_requirement`** (per capability) — distinct from
   `evidence_requirement`; what provenance the Gateway will supply for the
   resulting receipt.
5. **`non_claims`** (per capability) — the envelope carries non-claims today,
   but a capability-level list is what a progressive renderer needs.
6. **`retry_after_ms`** (on the `rate_limited` failure) — the client has the
   `rate_limited` recovery code and renders a "wait briefly and retry" hint,
   but has no Gateway-supplied wait to render or to type a retry against.

Backward-compatibility rule this lane proposes for all six: every field is
optional and additive; a descriptor without them renders exactly as it does
today, and the client shows an explicit "scope not declared by the Gateway"
line rather than inferring one. That keeps `ceal.version.v1` untouched, which
the request asks for.

Also, a small question rather than a request: `capability_access.readiness`
returned `unknown` for a granted target. Please state the closed vocabulary
and what a client should render for each value, since "granted but readiness
unknown" currently has no defined rendering.
