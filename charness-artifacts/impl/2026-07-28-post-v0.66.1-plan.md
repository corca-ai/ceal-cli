## Three judgments from the previous handoff that the review overturned

1. **`capability_ids` was listed as unblocked. It is not.** Every outbound
   request passes `decodeCealGatewayRequest` from the frozen protocol copy
   (`packages/ceal-client/src/http-transport.ts:76`), whose discovery validator is
   exact-key. A `capability_ids` body is rejected at egress, by this repository's
   own vendored validator, before the Gateway is reached. The work is unblocked
   by consuming `v0.66.1` (item 6), not by writing a CLI flag.
2. **The guard and the artifact consumption were treated as one slice. They are
   not.** Their proofs differ (injected fixtures vs archive digests plus install
   evidence), the second waits on another lane, and they end in opposite states —
   the guard slice closes red on purpose, the consumption slice closes green.
   Where they interlock is narrow and is handled by design: if the guard compares
   `pin.source.commit` against `lock.gateway.commit`, consumption becomes a data
   edit rather than a rewrite of the guard.
3. **The renderer re-verification was listed as work. It is a confirmation.**
   `ANNOUNCEMENT_POLICY_NOT_DECLARED` at `packages/ceal-worker-cli/src/index.ts:965`
   already carries the exact required wording, and the projection is applied
   before the concise view strips anything, so both output modes carry it.

## Item detail

**1 — ask `vinc` two questions.** The readback note supplies tag, commit, producer
tree, run id, artifact name, archive SHA-256, signature and certificate SHA-256,
and both package tarball digests. It does **not** supply
`handoff_manifest_sha256`, which `scripts/worker-gateway-handoff-archive.mjs:138`
requires of any lock and which can only be computed from
`gateway-artifact-handoff.json` inside the archive. So item 6 cannot be written
from the note alone, and this lane also has no stated path to the archive bytes.

**5 — the divergence guard.** Beyond flipping severity:

- Compare `pin.source.commit` against `lock.gateway.commit`. The pin's
  `shipped.protocol_tree` and `source.tree` are both author-written, so a verdict
  computed from them is a statement rather than a check — `docs/gates.md` already
  says so. Note the residual limit honestly in the same slice: `source.commit` is
  self-recorded too, so this makes divergence fatal without making convergence
  observable.
- Requirement 3 of the decision names four surfaces that must reject
  independently of which command ran. **None of them calls the verifier today** —
  `scripts/worker-release-inputs.mjs`, the three `build-worker-release-*.mjs`
  scripts, and `scripts/worker-acceptance-packet.mjs`. Reddening the gate alone
  satisfies requirement 1 and leaves requirement 3 unimplemented while looking
  finished.
- The development-only command is not optional in practice. The pin test lives in
  `test/contract/`, which `check:unit` runs, so the fatal guard reddens the
  iteration gate and the `pre-push` hook, not just `npm run check`.
- Four documents assert the now-false non-fatal rule: `AGENTS.md`, `docs/gates.md`,
  `docs/operator-acceptance.md`, and `README.md`. The third is the one a
  maintainer without Gateway access reads first.
- `test/contract/protocol-vendor-pin.test.mjs` argues in its own header that
  asserting "throws because diverged" against the live pin is wrong, because it
  punishes the fix it asks for. Reconcile deliberately: keep fatality in the
  fixture tier and update the live-pin assertion's reasoning rather than flipping
  it silently.

**6 — consuming the artifact.** Lock rebind, vendored re-sync to `ac602cc1`, and
re-pin must be one commit: the verifier fires `shipped_lock_mismatch` the moment
the lock moves without the pin. `release-contract.json` also still declares
`package_version: 0.65.0` for both protocol and client, which the version-identity
decision forbids as an identity anywhere in a release input.

Two consequences worth knowing before starting: rebinding the lock makes
`npm run accept:worker` fail against every currently installed release, because
`scripts/worker-acceptance-packet.mjs` compares the installed release's protocol
producer against the lock. And the "fresh Mac and Linux install/handshake
evidence" the readback note asks for is not a verification step — it needs an
installed signed release, therefore a push and a tag (two separate approvals),
therefore a new version number since `ceal-v0.66.1` is already taken, plus a live
session whose enrollment only the Gateway lane can issue. There is also no Mac in
this lane's reach, and CI's macOS leg runs the gate with the platform proofs
switched off.

**7 — parked.** The write-receipt readback needs an artifact beyond `v0.66.1`
(verified above). The attachment materialization note forbids implementing
against its route and lists five missing Gateway pieces; the only legitimate work
today is recording its client boundary constraints so a later slice does not
re-derive them.

## Also lane work, not yet scheduled

- **Version-as-identity sweep.** `release-contract.json` and the
  `required_gateway_protocol` block of `worker-release-inputs.json` name a package
  and version with no artifact tuple. The version-identity decision forbids that
  for any consumer proof, provenance sidecar, acceptance candidate, or release
  input. Natural home is item 6.
- **Do not harden the shared lock primitive.** The Gateway lane has committed to
  sharing it and porting the two recovery cases. The residual `createLock` race
  this lane owns is a separate thing and stays this lane's.

## The bypass this plan does not close

Editing `packages/ceal-protocol` and then updating the pin's `source.tree` to the
new hash passes every check in the repository. Nothing compares the vendored bytes
to anything the owner produced. That is the natural next move for whoever unblocks
`capability_ids` by hand, which makes it the most likely frozen-path violation in
this plan.
