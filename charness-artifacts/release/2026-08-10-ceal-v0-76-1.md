The signed Linux ARM64 worker embeds
`@corca-ai/ceal-protocol@0.72.13`, not the later local development packet. The
installed release manifest records tarball SHA-256
`cdcad0444df6a614b97be1ae4edf2a0b1de9cc04c82fe0888b0be43cde18f4e0`,
Gateway producer commit `b644bdcc1883a12f30dec9f15a918eca3676b740`, Gateway
tree `0a6a30d6f3d76077eb4ade02c43a069120011169`, and Protocol subtree
`07c79e9626a1ef0be3c3a3092ebff48a4433d70d`.

This is a build-input claim, not a `strings` inference. Re-check it by resolving
the installed binary, verifying its manifest and binary against the adjacent
`SHA256SUMS`, then comparing that manifest with the immutable tag inputs:

```sh
installed_binary=$(readlink -f "$(command -v ceal)")
installed_release=$(dirname "$installed_binary")
sha256sum "$installed_binary" \
  "$installed_release/ceal-worker-release-manifest-linux-arm64.json" \
  "$installed_release/SHA256SUMS"
git show 'ceal-v0.76.1^{}:gateway-protocol-handoff-lock.json'
git show 'ceal-v0.76.1^{}:packages/ceal-protocol/package.json'
git rev-parse 'ceal-v0.76.1^{}:packages/ceal-protocol'
```

The release workflow digest-checks the locked Gateway handoff and installs its
packed Protocol tarball into the isolated client/worker build before bundling
the staged worker entry point. `ceal version`'s `protocol_version: 1.3.0` is the
wire negotiation version; it is a different fact from the npm contract-artifact
version above.

to `ceal-v0.76.0` changes future stable resolution only; a host already on
0.76.1 needs the explicit signed 0.76.0 installer path for an intentional
downgrade.
